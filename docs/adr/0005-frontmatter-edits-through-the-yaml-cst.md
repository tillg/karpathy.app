# The properties form edits frontmatter through the YAML CST and refuses lossy edits

The properties form (#82) never re-serializes a note's frontmatter. A scalar is changed with `yaml`'s `CST.setScalarValue` and the tokens are stringified back, which keeps the quoting style and the comments; list items and new keys are text splices at the node's source range. Every result then has to pass one invariant (`checkEdit` in `apps/web/src/lib/frontmatter.ts`): it parses without errors, every other property reads back the same and in its place, only the edited property's lines changed, and the edited value reads back as intended. Otherwise the edit is **refused** ("Edit this property in YAML"), and nothing is written. We rejected `Document.toString()`, whose own docs call its comment handling unstable and which picks its own scalar style, and js-yaml (no CST at all). Both would make every form edit a diff of the whole block. A "closest possible" rewrite is also off the table: the rule from [ADR 0003](0003-codemirror-raw-markdown-editor.md), that untouched text stays byte for byte the same, wins over convenience. Property-based tests (`fast-check`) and the demo vault's frontmatters check the guarantee and that refusals stay rare. A new edit kind must go through the same invariant.
