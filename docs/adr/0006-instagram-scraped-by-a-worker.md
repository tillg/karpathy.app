# Instagram is scraped by a worker on the user's machine, which pulls jobs from the server

Instagram blocks scraping from data-centre IPs (#137), so in worker mode the server no longer fetches Instagram posts itself. An **Instagram worker** (`tools/instagram-worker/`, command `karpathy-instagram-worker`, a pipx-installed Python package run by launchd or `systemd --user`) on a Mac or Linux box with a home IP **pulls** jobs: it claims one post at a time from `POST /api/ingest/instagram/jobs/claim`, scrapes it with instascraper and its own Instagram session, and uploads the result as a tar.gz that the backend streams to the ingest service. A job is a shortcode, derived by scanning the vaults' `Input/*/index.md` for Instagram links that wait; the worker only makes outbound calls, so nothing on the server has to reach the user's machine. **ingest-email stays the only writer of `Input/`:** the ingest service only checks and unpacks an upload into a results dropbox (`/state/instagram/results/<shortcode>/`), and ingest-email's Instagram resolver maps it from there with the same `map_output` as before; while there is no result the link *waits* without counting an attempt, and failures are counted per post in the dropbox (backoff, permanent after 5). Neither the backend nor `server.py` ever edits a vault file, so naming, dedup and the per-profile lock stay in one place and nothing races the resolve loop. **The worker's token is scoped:** a separate deploy secret `ingest_worker_token`, accepted only on the five job and heartbeat routes (a router mounted before the main `bearerAuth`); a stolen token can claim jobs and upload results, which land only as `Input/` items the user reviews, but can't read or change a vault. The Instagram session and password never leave the worker's machine. We rejected the **Mac relay** (`instagram-mac-relay`: the server's egress proxy forwards Instagram traffic to a forward proxy on the Mac), because it needs the Mac reachable as a server over Tailscale plus an untested Docker → tailnet route, and the user asked for the pull-based worker. We rejected the **browser** too: a PWA `fetch` can't read instagram.com (no CORS headers for our origin, HttpOnly `sessionid` on another origin, our own `connect-src 'self'`), and a browser extension would mean porting the scraper to JavaScript against Instagram's undocumented web API, running only while a browser is open and as the user's main account. A residential proxy service stays the fallback if no worker is awake often enough. Links wait while no worker runs; the app shows that. One Instagram account per worker (the app warns, it doesn't enforce). Setup: [../instagram-worker.md](../instagram-worker.md).
