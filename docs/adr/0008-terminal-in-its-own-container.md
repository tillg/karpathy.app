# The terminal is a shell in a container of its own, confined like ingest, with no app secrets

The app's **Terminal** panel (#175, a bottom panel like VS Code's) gives the user a real shell on the server's vaults, and Claude Code in it, from the iPad as well as the Mac. The shells run in a **`terminal` compose service** (image `karpathy.app-terminal`, `apps/terminal` + `deploy/terminal/`), not in the backend: a small PTY server (node-pty) runs bash as uid 1000, starting in the open vault's folder (`/vaults/<id>[/<root>]`), with all vaults mounted read-write, git, ripgrep, curl, less and Claude Code (2.1.318, pinned, auto-update off). Its home `/home/node` is the volume `terminal-home`, so the Claude login, `~/.claude` and shell history survive restarts and deploys. The container is confined like ingest: network `internal` only, `HTTP(S)_PROXY` to the egress proxy, `cap_drop: [ALL]`, `no-new-privileges`, no published port, **no app secret**. Its one secret, `terminal_token`, only lets the backend into the terminal service. The backend keeps the public routes (`/api/terminals…`, bearer token) and forwards them to `http://terminal:8095` with that token. **Why not in the backend:** Claude Code is an AI that reads untrusted vault content (ingested mail, web pages), so prompt injection reaches whatever its shell can read. In the backend container that is the GitHub token, the bearer token and the opencode password, plus a direct route to the internet. In its own container a hijacked session can damage vault files (uncommitted, visible in Changes) but can't take a credential, and it reaches the internet only through the egress proxy. We started with the shell in the backend and moved out once Claude Code became a requirement. The host (Docker socket, `nsenter`, SSH) was rejected too: it would undo the hardening that stops a container breakout short of root. For host-level work there is still SSH over Tailscale.

**Transport:** NDJSON over `fetch` plus POSTs, no WebSocket (it can't send the `Authorization` header and would bypass `bearerAuth`): `GET /api/terminals/:tid/stream?from=N`, `POST …/input`, `POST …/resize`, `DELETE`, `GET /api/terminals`, `POST /api/vaults/:id/terminals {cols,rows}`. **Sessions live until the user closes them** (✕, `DELETE`) or the shell exits (its background jobs are killed with it), at most 4, so a running command survives a closed panel, a reload, the iPad sleeping or another device; only a restart of the terminal container (a deploy) ends them. The service keeps the last 256 KB of output per session; one stream is attached at a time, so a second device or tab takes the session over (the first gets a `taken` event and shows "Opened on another device or tab" with **Use here**); a reattach resumes from the page's last offset, or replays the 256 KB and nudges the size so full-screen programs repaint. We rejected a 5-minute grace after a dropped stream (it would kill a long Claude Code run) and tmux in the image (one more layer to learn). **A `terminal.enabled` setting** (`deploy/settings/`, on everywhere) switches it off: the routes then answer `404 terminal-off` and the app shows no button.

**Consequences for security:** the bearer token now grants a shell (uid 1000 in the terminal container: read and write every vault, internet through the egress proxy). The terminal has no git push credentials and, with the git dirs read-only, can't commit: commits go through the app (ADR 0001) and its secret scan. A user who logs in to GitHub there does so at their own risk, but a push from there has no commits to push. Because the terminal can write the vaults' working trees, **each vault's git directory lives outside them**, in `/gitdirs/<id>` on a `gitdirs` volume that only the backend mounts read-write (terminal and opencode read-only, ingest not at all). The working tree keeps a `.git` file (`gitdir: /gitdirs/<id>`), so `git status`, `log` and `diff` work in the terminal, while commit, pull and push fail: **git in the terminal is read-only**, commit with the app. The terminal can't write config, hooks or refs, so it can't plant a `filter`, `textconv`, hook or fake `origin/<branch>` that would run in the backend next to the GitHub token or empty the push scan's range. Every backend git command gets `GIT_DIR` and `GIT_WORK_TREE` explicitly (`repoEnv`) and never discovers a `.git` in the tree, runs with `core.hooksPath=/dev/null`, `core.fsmonitor=false` and `diff.ignoreSubmodules=all` (a repo the terminal `git init`s inside a vault is never entered); the backend's temp files in the `/vaults` root get random names and `O_EXCL` (a planted symlink can't redirect them), and the scanned-commits record lives in `/config`. The first start of a backend with this volume moves each existing vault's `.git` there (copy, rename into place, swap for the file; idempotent); rolling back to a release that expects `.git` folders needs the reverse copy first. We first guarded the backend with an allowlist on `.git/config` (`409 unsafe-git-config`); a review broke it (`.git/commondir`, a fooled stamp cache, `update-ref` on the remote-tracking ref, a scan-then-push race) and it turned common keys (`git lfs`, `submodule.*`) into refusals, so it was removed. Also rejected: running the terminal as a second uid with ACLs (the backend lost write access to files the terminal made with mode 0600/0700, so Commit, Discard and vault delete failed). Claude Code in the terminal is an AI reading untrusted content, a prompt-injection path in the user's own session; the guard is the confinement above, not a prompt. Provider-agnostic stays the rule for the app's agentic loop (opencode); a vendor CLI in the user's own terminal is a tool, not that loop.
